# С чего начать: набор для первых месяцев

> Из большого рабочего набора выделено то, что реально нужно новичку.
> Порядок — по времени подключения, а не по важности.

---

## Сразу: три официальных плагина

Ставятся командой `/plugin` в Claude Code, из официального маркетплейса Anthropic.

| Плагин | Что даёт | Когда срабатывает |
|---|---|---|
| **feature-dev** | Проектирует фичу до кода: смотрит проект, предлагает архитектуру, план файлов | «Добавь функцию…», «реализуй…» |
| **code-review** | Ревью изменений: баги, дыры, лишние усложнения | Перед коммитом, `/code-review` |
| **commit-commands** | Нормальные коммиты и pull request одной командой | `/commit`, `/commit-push-pr` |

Этих трёх хватает на первый месяц. Они закрывают полный цикл: спроектировал → сделал → проверил → сохранил.

## Через пару недель

| Плагин / скилл | Что даёт |
|---|---|
| **frontend-design** | Помогает делать интерфейсы, которые не выглядят шаблонными |
| **skill-creator** | Помогает писать собственные скиллы — по сути, скилл про скиллы |
| **claude-md-management** | Обновляет CLAUDE.md по итогам сессии: что выучили — то записали |
| **security-guidance** | Проверка на утечки ключей и типовые дыры |

## Свои скиллы: с каких начать

Не скачивать, а **написать самому** — под свои задачи. Четыре штуки, которые пригодятся почти всем:

### 1. `my-stack` — твой стек по умолчанию

```markdown
---
name: my-stack
description: Применять при выборе технологий для нового проекта или модуля — фиксирует стек по умолчанию
---

# Стек по умолчанию

- Скрипты и данные: Python 3.12, pandas, openpyxl
- Телеграм-боты: aiogram 3
- Веб: Next.js + Tailwind
- База: SQLite, пока не нужен многопользовательский доступ
- Тесты: pytest

Отклоняешься от списка — сначала объясни почему.
```

### 2. `project-start` — как начинать проект

```markdown
---
name: project-start
description: Использовать в начале нового проекта — задаёт порядок: сначала спецификация, потом код
---

# Начало проекта

Порядок обязателен:
1. Задать вопросы, собрать SPEC.md — что программа делает и чего не делает
2. Собрать PLAN.md — шаги, у каждого проверяемый результат
3. git init и первый коммит с этими двумя файлами
4. Только потом код, по одному шагу за раз

Не начинать с кода. Не делать больше одного шага за запрос.
```

### 3. `explain-me` — объяснять как новичку

```markdown
---
name: explain-me
description: Использовать, когда пользователь просит объяснить код, ошибку или технологию
---

# Объяснения

- Простыми словами, без жаргона. Термин ввёл — сразу расшифруй в скобках
- Сначала «что это делает», потом «как устроено»
- Аналогии из жизни приветствуются
- В конце — где это может сломаться
- Не больше пяти абзацев за раз
```

### 4. `before-commit` — что проверить перед сохранением

```markdown
---
name: before-commit
description: Использовать перед git commit — проверка изменений на ключи, баги и мусор
---

# Проверка перед коммитом

1. Нет ли в изменениях ключей, токенов, паролей, файлов .env
2. Не осталось ли отладочных print и закомментированного кода
3. Работает ли то, что менялось — запусти и покажи результат
4. Сообщение коммита: что сделано и зачем, одной строкой на русском
```

## Как ставить

Каждый скилл — папка с одним файлом:

```bash
mkdir -p ~/.claude/skills/my-stack
code ~/.claude/skills/my-stack/SKILL.md
```

Либо попроси агента:

```text
Создай четыре скилла из файла 03-скиллы/02-рекомендуемый-набор.md
в папке ~/.claude/skills/. Содержимое возьми оттуда, ничего не выдумывай.
```

## Чего не ставить в начале

В большом рабочем наборе есть целые тематические блоки — SEO (около 30 скиллов),
дизайн, тестирование браузером, работа с маркетплейсами, генерация изображений.
Всё это отличные инструменты **под конкретную работу**, но новичку они мешают:

- увеличивают шанс, что подхватится не тот скилл;
- заслоняют главное — привычку думать до кода;
- создают ощущение, что инструмент важнее умения.

Правило: **скилл подключается, когда появилась задача, а не заранее.**
