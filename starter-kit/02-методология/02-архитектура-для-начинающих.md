# Архитектура: минимум, который нужно понимать

> Архитектура — это не диаграммы и не умные слова. Это ответ на вопрос:
> **где что лежит и кто с кем разговаривает.**
> Пять принципов ниже покрывают 90% задач, с которыми ты столкнёшься в первый год.

---

## Принцип 1. Раздели ввод, логику и вывод

Любая программа делает три вещи: **получает данные → что-то с ними делает → отдаёт результат.**
Эти три части должны жить в разных местах.

```text
Плохо (всё в одном файле, 300 строк):
main.py  ← читает Excel, считает прибыль, рисует таблицу, шлёт в телеграм

Хорошо:
input.py       ← только читает файлы, ничего не считает
calculate.py   ← только считает, не знает про файлы и телеграм
output.py      ← только сохраняет и отправляет
main.py        ← связывает их в нужном порядке, 20 строк
```

Зачем это нужно на практике:

- Поменялся формат исходного файла — правишь один `input.py`, расчёт не трогаешь.
- Нужно проверить формулу — запускаешь `calculate.py` на выдуманных числах, без Excel.
- Захотел вместо телеграма отправлять на почту — меняешь только `output.py`.

**Признак нарушения:** функция, которая одновременно читает файл и считает.
Такую невозможно проверить, не подсунув ей файл.

## Принцип 2. Одна функция — одно дело

Функция должна делать что-то одно, и её название должно об этом честно говорить.

```python
# Плохо: название врёт, функция делает четыре дела
def process(file):
    data = read_excel(file)
    for row in data:
        row["profit"] = row["sell"] - row["buy"]
    save_excel(data, "out.xlsx")
    send_telegram("Готово")

# Хорошо: три честные функции
def read_products(path): ...
def add_profit(products): ...
def save_report(products, path): ...
```

Практическое правило: **если в описании функции появляется «и» — её надо разделить.**
«Читает файл и считает прибыль» — две функции.

Второе правило: если функция не помещается на экран целиком — скорее всего, в ней спрятаны две.

## Принцип 3. Настройки — отдельно от кода

Всё, что может измениться без изменения логики, выносится наружу:
пути к файлам, ключи API, проценты комиссий, адреса серверов.

```python
# Плохо: значения размазаны по коду
commission = price * 0.15
api_key = "sk-abc123..."
path = "/Users/ivan/Desktop/products.xlsx"

# Хорошо: config.py и .env
# config.py — то, что не секретно
COMMISSION_RATE = 0.15
DEFAULT_INPUT = "data/products.xlsx"

# .env — то, что секретно, и что НИКОГДА не попадает в Git
OPENAI_API_KEY=sk-abc123...
```

Файл `.env` обязательно вносится в `.gitignore`. Ключ, уехавший в публичный репозиторий,
находят автоматические сканеры за минуты — это не страшилка, а рутина.

## Принцип 4. Данные — в одном месте

Как только у программы появляется «память» — что-то, что должно жить между запусками —
нужно решить, где это лежит, и не разводить зоопарк.

Лестница усложнения, поднимайся по ней только когда прижмёт:

| Что храним | Чем |
|---|---|
| Несколько настроек | Файл `.env` или `config.py` |
| Список на сотню-другую строк | CSV или JSON-файл |
| Данные, по которым нужен поиск и фильтры | SQLite — файл базы, ничего ставить не надо |
| Несколько человек работают одновременно | PostgreSQL — вот здесь и понадобится Docker |
| Данные из внешнего сервиса | Не храним, запрашиваем каждый раз. Кэшируем, если медленно |

Типичная ошибка — начать с PostgreSQL там, где хватило бы JSON-файла на 50 строк.
Обратная ошибка — держать в CSV то, что уже требует поиска по трём полям и связей между таблицами.

## Принцип 5. Границы с внешним миром

Всё, что уходит за пределы твоей программы — сеть, файлы, чужие API — **может отказать**.
Не иногда, а регулярно: интернет пропал, сервис недоступен, файл переименовали, лимит запросов исчерпан.

Правило: **код, который ходит наружу, живёт в отдельном месте и всегда предполагает отказ.**

```python
# Плохо: запрос в середине бизнес-логики, отказ роняет всё
def calculate_profit(product):
    rate = requests.get("https://api.cbr.ru/rate").json()["usd"]
    return product["price"] * rate

# Хорошо: работа с сетью отдельно, есть запасной вариант
def get_usd_rate():
    """Курс из ЦБ. Если недоступен — берём последний сохранённый."""
    try:
        return requests.get("https://api.cbr.ru/rate", timeout=5).json()["usd"]
    except Exception:
        return load_cached_rate()

def calculate_profit(product, rate):   # чистый расчёт, ничего не знает про сеть
    return product["price"] * rate
```

Расчёт, который не ходит в интернет, можно проверить мгновенно и сто раз подряд.
Расчёт со встроенным запросом проверяется только при живом интернете и работающем сервисе.

## Как выглядит нормальная папка проекта

```text
my-project/
├── .env                 ← ключи и пароли, в Git не попадает
├── .gitignore           ← что не отправлять в Git
├── README.md            ← что это за проект и как запустить
├── SPEC.md              ← что программа должна делать
├── requirements.txt     ← список библиотек (Python)
├── config.py            ← настройки, не секретные
├── src/                 ← сам код
│   ├── input.py
│   ├── calculate.py
│   └── output.py
├── data/                ← входные и выходные файлы
└── tests/               ← проверки
```

Не обязательно заводить всё это в первый день. Но когда файлов в проекте становится больше пяти —
раскладывай по папкам, пока это ещё дёшево.

## Три вопроса для проверки архитектуры

Задавай их себе (и агенту) раз в несколько дней:

1. **«Если поменяется формат входного файла — сколько файлов придётся править?»**
   Больше одного — ввод не отделён от логики.

2. **«Можно ли проверить расчёт, не имея под рукой Excel, интернета и базы?»**
   Нельзя — логика слиплась с внешним миром.

3. **«Найду ли я через месяц место, где считается комиссия, за минуту?»**
   Нет — плохие имена или всё свалено в один файл.

Хороший промпт агенту раз в неделю:

```text
Посмотри структуру проекта и скажи: что здесь усложнено сверх необходимого,
а что наоборот скоро развалится. Не правь, просто перечисли и объясни почему.
```

## Чего НЕ надо делать в начале

Список вещей, которые кажутся «правильными», но новичку только мешают:

- **Микросервисы.** Это решение проблемы больших команд, а не маленьких программ.
- **Слои с абстрактными интерфейсами «на случай смены базы».** Базу вы не смените.
- **Своя система плагинов.** Пока плагинов нет — она обслуживает саму себя.
- **Универсальные функции «на любой случай».** Универсальность = никто не понимает, что оно делает.
- **Преждевременная оптимизация.** Сначала пусть работает, потом — если реально медленно — ускоряй.

Ориентир: **самое простое решение, которое работает.** Усложнять будешь, когда упрёшься —
и тогда это будет обоснованное усложнение, а не гадание.
